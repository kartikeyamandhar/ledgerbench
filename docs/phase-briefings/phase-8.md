# Phase 8 Briefing — Launch

Status: proceeding under standing autonomy grant (2026-06-12); briefing delivered with the build.
Depends on Phase 6 only (Phase 7 also happens to be complete).

**Objective:** package, publish, run the benchmark, ship the finding. Executed in two
tiers, honestly separated: everything achievable keyless/offline ships now; the steps
gated on credentials only the owner holds (API keys, PyPI account) ship as a precise
punch list with every command ready to paste.

## 1. Concepts (theory level)

- **Reproducible release engineering.** Trusted publishing (OIDC) over long-lived
  tokens: the release workflow proves its identity to PyPI cryptographically; no secret
  to leak. The Docker image pins the same wheel CI tested. A release is a build you can
  re-derive, not an artifact you bless.
- **Selective prediction & calibration (the deferred Phase-2 thread).** Traces have
  carried `confidence` since the contract froze. With real runs, confidence-vs-accuracy
  curves measure whether agents *know when they don't know* — the report's calibration
  section computes them from recorded data, no new instrumentation.
- **Claims discipline.** The report's limitations section is reviewed against every
  headline sentence; numbers appear only with a committed manifest behind them. The
  naive baseline's gap (100% ran fine / 9% business-correct) is a *floor*
  demonstration, labeled as such; the frontier A/B finding is published only after the
  key-gated runs execute.

## 2. Design (architecture level)

- **`release.yml`:** on tag `v*`: build sdist+wheel (`python -m build`), `twine check`,
  publish to PyPI via trusted publishing (`pypa/gh-action-pypi-publish`, OIDC — *no
  token stored*); then build the Docker image and push to GHCR with the workflow's
  `GITHUB_TOKEN`. PyPI publishing activates the moment the owner registers the trusted
  publisher (punch list); until then the workflow's publish job fails cleanly without
  blocking the GHCR job.
- **`Dockerfile`:** slim Python 3.12 base, wheel install, `ledgerbench` entrypoint;
  demo runs offline inside the container (the smoke acceptance).
- **Benchmark results (`benchmark/results/`):** committed JSONL traces + manifests for
  the runs that can execute keyless — the naive baseline, both conditions, 3 seeds over
  the public 150. Frontier agents land in the same layout when keys exist; results are
  append-only, never edited (corrections are new runs).
- **Leaderboard (`benchmark/leaderboard/`):** a static single-file page generated by
  `scripts/build_leaderboard.py` from committed manifests + verdict summaries — same
  no-JS SVG style as the report; per-axis columns beside the aggregate (the
  weights-nitpick defense); private-split column marked "local only, aggregates".
  Deployed by `pages.yml` (GitHub Pages via actions) — enabling Pages on the repo is a
  one-click owner step if the API call is refused.
- **`docs/report.md`:** the technical report — motivation, taxonomy, method (ground
  truth by construction, the five axes, fail-closed grain checking with published
  TPR/FPR), the naive-floor results with the gap chart, limitations, future work.
  Sections that need frontier numbers carry explicit `[pending keyed runs]` markers
  rather than projections.
- **Version/`CITATION.cff` → 1.0.0; tag `v1.0.0` on merge.**

**Alternatives considered:** waiting for keys before any launch work (rejected: Phase 8
explicitly must not block on externalities; RT-007's whole point); fabricating
"expected" frontier numbers (rejected outright — claims discipline); TestPyPI dry run
in CI on every push (rejected: trusted publishing covers it; release flow validated by
`twine check` + container smoke).

## 4. Red-team summary (§13)

- **DevOps (leads):** OIDC publishing means no PyPI secret exists to leak; GHCR uses
  the ephemeral workflow token; the release is tag-triggered and reproducible.
- **Security:** results contain no keys (trace redaction is by construction — headers
  never serialized); publishing tokens don't exist; the container runs as non-root.
- **End User:** `pip install ledgerbench && ledgerbench demo` is the contract; the
  leaderboard shows per-axis numbers beside the aggregate, always.
- **Product:** the naive floor row makes the leaderboard non-empty and honest on day
  one; "pending" beats "projected".
- **SW Engineer:** the roster runner reuses `run`'s machinery; resume = skip existing
  result directories (manifest presence is the marker).
- **Staff:** results-as-committed-files keeps the leaderboard a pure function of the
  repo — re-render anytime, audit anything.
- **Failure modes:** PyPI name squatting (the name is registered at first publish —
  punch list is explicit about doing this promptly); rate limits mid-run (per-provider
  overnight runs + resume; budget hard cap 150 USD); Pages API permission (fallback:
  one-click manual enable, documented).
- **Register add: RT-017** — launching with a naive-only leaderboard risks "toy"
  perception; mitigated: the floor row is explicitly framed as the gap demonstration,
  the punch list makes frontier runs a paste-one-command step, and the report's
  pending-markers keep claims honest.
