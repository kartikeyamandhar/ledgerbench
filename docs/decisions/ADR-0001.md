# ADR-0001: Toolchain and project layout

Date: 2026-06-10
Status: accepted

## Context

LedgerBench is a benchmark whose own credibility depends on reproducibility and
hygiene. Phase 0 must produce a skeleton that every later phase drops code into without
re-touching configuration. The forces in play: keep the dependency tree small and
auditable; single-source metadata; make "green" a binary, identical gate locally and in
CI; enforce security and authorship invariants from the first commit; and avoid
over-engineering a foundation for a solo developer.

## Decision

- **`src/` layout.** The package lives at `src/ledgerbench/`, importable only when
  installed. Tests run against the installed package, not the working tree.
- **`pyproject.toml` as the single source of truth**, with **hatchling** as the build
  backend and the version single-sourced from `src/ledgerbench/__init__.py`
  (`[tool.hatch.version]`).
- **ruff** for both lint and format (line length 100); **mypy strict** on `src`,
  relaxed on `tests`; **pytest + pytest-cov + hypothesis** for tests.
- **One gate, one command:** `make check` = format check + lint + type + tests with the
  coverage gate. CI runs the identical steps on Python 3.11 and 3.12.
- **Security and authorship from commit zero:** gitleaks + file-hygiene pre-commit hooks;
  `.env.example` placeholders only; `.claude/settings.json` sets
  `includeCoAuthoredBy: false`; commits carry no co-author or tool-attribution trailers.
- **Coverage gating, phased:** Phase 0 enforces only the 85% global gate. The 100% branch
  gates on `scorer/` core (`reconcile`, `actions`, `aggregate`) and `runner/safety.py`
  are wired in their owning phases (2 and 4), when those modules contain branchable logic.
  Enforcing 100% branch coverage on empty stubs is vacuous and would hide, not prevent,
  under-testing.

## Alternatives

- **Flat layout** (package at repo root): rejected — it lets tests import the working tree
  and masks "missing from the wheel" packaging bugs. `src/` makes install-correctness a
  test-time property.
- **setuptools / pdm-backend** instead of hatchling: both workable; hatchling chosen for
  the cleanest `src/` + dynamic-version support with the least boilerplate. The choice is
  isolated to `[build-system]` and is cheap to revisit.
- **Separate black + flake8 + isort** instead of ruff: rejected — more tools, slower,
  more config; ruff covers all three with one dependency.
- **`requirements.txt` only** vs a frozen lock: rejected — a committed `requirements.lock`
  (via `pip freeze` in the venv) makes a reviewer's environment byte-identical to the
  maintainer's, which a loose requirements file cannot guarantee.
- **Single Python version in CI**: rejected — the portability claim needs the 3.11/3.12
  matrix; `requires-python = ">=3.11"`.

## Red-team

- **Failure modes.** Scope creep into application logic during scaffolding — mitigated by
  the Phase 0 rule (no body beyond `pass` / docstring / `NotImplementedError`) and the
  walk-import test that would surface accidental import-time logic. Toolchain drift —
  mitigated by pinned dev tools and a committed lock.
- **Edge cases.** A fresh clone before `make venv install` has no `agentic_flow/`, so the
  local mypy pre-commit hook (pointed at `agentic_flow/bin/mypy`) is unavailable until
  setup; this matches the documented quickstart order and CI does not rely on it.
- **Security.** Secrets cannot enter history undetected (gitleaks active from commit one);
  the SQL-execution threat model is documented in SECURITY.md before any executor exists.
- **Scalability / maintainability.** `pyproject` single-sourcing and the `contracts/`
  dependency-sink layout keep module boundaries explicit as the codebase grows; one gate
  command keeps the dev/CI contract from diverging.

## Consequences

- **Easier:** every later phase adds code into a known, gated tree; CI green is a precise
  merge precondition; authorship and secret-hygiene are mechanically enforced.
- **Harder (intentionally):** logic must be installed to be tested (no path hacks);
  contract changes are deliberately expensive (schema re-export + version bump in later
  phases). Per-module 100% branch gates are deferred, which is recorded here so the
  deferral is explicit rather than forgotten.
