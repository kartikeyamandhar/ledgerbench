# ADR-0002: Rulebook YAML as the canonical semantic source

Date: 2026-06-11
Status: accepted

## Context

LedgerBench grades agents against declared business semantics, and gold must derive
from those semantics mechanically (never from a model or an opinion). Phase 1 builds
two deterministic worlds. Two questions had to be answered: in what form are a world's
semantics declared, and how do downstream phases consume them. The constraint that
matters most long-term is Phase 7 (BYO): a real dbt project must feed the *same* engine,
so whatever structure the rulebook produces is also the structure a dbt manifest must
compile into.

## Decision

- **The rulebook is YAML, and it is the law.** Each world ships a `rulebook.yaml`
  declaring tables (with grains and primary keys), relationships (with cardinalities),
  metrics (measure, `value_type`, filters, exclusions, grain), and the documented
  metadata the trap taxonomy needs preconditions for: ambiguities, absent dimensions,
  and a reporting timezone / fiscal-year offset. Planted irregularities (nulls,
  duplicates) are declared too, so the data can be realistic without making gold
  uncomputable.
- **Two canonical structures, consumed everywhere; YAML touched in one place.**
  `ingestion/rulebook.py` validates the YAML (pydantic v2) and projects it into a
  `DefinitionRegistry` (metrics) and a `GrainModel` (table grains + relationship
  cardinalities). No other module reads YAML. In Phase 7, `ingestion/dbt_manifest.py`
  compiles a dbt manifest into the *same* two structures, so BYO mode swaps the loader
  and changes nothing downstream. This is the project's central architectural bet.
- **Generators are seeded, offline, stdlib-only.** `benchmark/worlds/<name>/generate.py`
  exposes `build(con, seed)` using one `random.Random(seed)`; no numpy, no Faker, no
  wall-clock, no network. A thin `src/ledgerbench/worlds.py` (added this phase; not in
  CLAUDE.md section 9) runs the schema, invokes the generator, and writes a gitignored
  `.duckdb`, so the CLI stays a thin shell.
- **Determinism is checked by content hash, not file bytes.** `world_digest` hashes each
  table's rows read in a fully-ordered way. Raw `.duckdb` bytes are not stable across
  DuckDB versions; content is. Same seed -> identical digest; a different seed -> a
  different digest with an identical schema.

## Alternatives

- **Python or JSON rulebooks:** rejected. YAML is human-authored and supports inline
  comments, which is how each planted precondition is documented next to where it lives.
  Validity is still enforced by pydantic, so YAML's looseness is contained.
- **Bake gold values into the world:** rejected. Gold is derived from the rulebook later
  (Phase 5), so a world regeneration or a tolerance change re-derives gold consistently.
- **numpy / Faker for generation:** rejected per the small-dependency rule, and because
  explicit seeded stdlib randomness makes byte-reproducibility easy to reason about.
- **Hash the raw database file:** rejected as fragile across DuckDB versions; the content
  digest is the meaningful invariant.
- **Describe worlds entirely inside `src`:** rejected. Worlds are data; keeping `schema.sql`
  + `generate.py` + `rulebook.yaml` together under `benchmark/worlds/<name>/` matches
  section 9 and keeps a world self-contained.

## Red-team

- **Hidden nondeterminism** (dict/set ordering, wall-clock, unseeded calls) would break the
  reproducibility claim. Mitigated by routing all randomness through one seed, avoiding the
  clock, and the golden hash tests that would fail on any drift. (Register RT-010.)
- **Rulebook/dbt divergence** would make Phase 7 expensive. Mitigated by shaping the
  rulebook around dbt concepts now (entities/relationships, measures, filters) and pinning
  the registry as the shared target here.
- **Worlds too clean / too messy:** deliberate, *documented* nulls and duplicates keep them
  credible while gold stays computable; every irregularity is declared in the rulebook.
- **Security:** generators are offline and write only inside the workspace; the rulebook is
  parsed, never executed.

## Consequences

- **Easier:** swapping the semantic source (rulebook today, dbt tomorrow) changes only the
  loader; gold derivation, scoring, and reporting are untouched. Determinism is testable.
- **Harder (intentionally):** every metric and relationship must be declared explicitly; an
  undeclared table reference is a validation error, not a silent pass.
